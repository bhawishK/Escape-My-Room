# Prepared room decision

Issue 2 loads this one prepared room. It is a stand-in, not a scan of a physical room. Later issues may replace the shapes with a real reconstruction if the IDs below stay the same. Issue 23 adds a second manifest form with one GLB per entity, rotations and several movable entities; see [Multi-asset rooms](#multi-asset-rooms-issue-23). The stand-in room keeps its original form and rules.

## Coordinate frame

- Units are meters.
- The origin is the center of the floor.
- +X is right, +Y is up, +Z is toward the viewer. This matches the current diagnostic camera, which sits on +Z and looks toward -Z.
- glTF is Y-up and right-handed.
- An entity position is the center of that object's bottom face. Furniture and the box rest on the floor at y = 0.
- Rotations are unit quaternions in `(x, y, z, w)` order, the glTF order. The stand-in room has none; both clients receive the identity rotation for it.
- The floor is the exception: it is a 0.02 m slab whose top surface is y = 0, so its position is `(0, -0.02, 0)`.

Room version is the integer `1`.

## Entities

Mesh names inside the model file are not IDs. These manifest IDs are the identities both clients must use.

| ID | Kind | Selectable | Size (width × height × depth) | Position (bottom center) |
| --- | --- | --- | --- | --- |
| `floor` | static | no | 4.00 × 0.02 × 4.00 m | `(0, -0.02, 0)` |
| `desk` | static | no | 1.20 × 0.75 × 0.60 m | `(0, 0, -1.20)` |
| `cabinet` | static | no | 0.80 × 1.20 × 0.40 m | `(1.40, 0, -1.20)` |
| `box` | movable | yes | 0.20 × 0.20 × 0.20 m | `(-0.50, 0, -0.40)` |

Width is along X, height along Y, depth along Z. The desk and cabinet sit toward the far side of the floor and do not overlap. The box sits on the floor in front of the desk, closer to the viewer. Only `box` may later be moved. Moving it must not move `floor`, `desk`, or `cabinet`.

Selection behavior is issue 5. The selectable flag is recorded now so the manifest can distinguish the box from the furniture.

## Asset files

`assets/prepared-room/build_room.py` writes three files from the table above:

- `manifest.json` holds room version `1`, the entity IDs, kinds, flags, sizes, and positions. This file is the identity contract.
- `room.gltf` holds four separate meshes. Each mesh origin is the center of that object's bottom face. A node name is only a pointer; it is not the entity ID.
- `room.bin` holds the vertex data for those meshes.

Node translations in `room.gltf` are copied from the manifest positions, so opening the model shows the same layout as the table.

## How the files are produced

From the repository root, run `python3 assets/prepared-room/build_room.py`. It rebuilds `manifest.json`, `room.gltf`, and `room.bin` from the entity table in this document. Change a size or position in that script, then run it again. Do not edit the model and the manifest separately.

Python loads the manifest when the server starts. It refuses the room if the model is missing, a listed object has no mesh of its own, a model position disagrees with the manifest, a node is rotated, scaled or sits under a transformed parent, or a mesh's extent disagrees with the listed size and bottom-center pivot. Both devices then see the same error instead of two different rooms.

## What was checked

Automated checks cover the shared version and entity list, a box move that leaves the floor, desk, and cabinet in place, rejection of a furniture move, a wrong room version being removed from the session, and a missing model file.

A desktop browser at `http://127.0.0.1:8000` showed the gray floor, brown desk, darker cabinet, and teal box after **Connect phone**, with the status `Room version 1 · floor, desk, cabinet, box (movable)`. iPhone and Quest observations for this room are not recorded yet. Open the same HTTPS address used for the connection test and confirm both devices show that same status.

## Multi-asset rooms (issue 23)

`assets/multi-asset-room/` is a deterministic fixture in the second manifest form. It is the shape AI-generated rooms will be published in; nothing here is generated by AI. Rebuild it with `python3 assets/multi-asset-room/build_room.py`.

| ID | Kind | Selectable | Asset | Size (W × H × D) | Position | Rotation |
| --- | --- | --- | --- | --- | --- | --- |
| `floor` | static | no | `floor.glb` | 3.00 × 0.02 × 3.00 m | `(0, -0.02, 0)` | none |
| `table` | static | no | `table.glb` | 1.00 × 0.75 × 0.60 m | `(0, 0, -1.00)` | none |
| `mug` | movable | yes | `mug.glb` | 0.092 × 0.10 × 0.08 m | `(0.25, 0.75, -0.95)` | none |
| `book` | movable | yes | `book.glb` | 0.20 × 0.04 × 0.15 m | `(-0.20, 0.75, -1.05)` | 30° about +Y |

The mug and book rest on the table top. Their assets contain child transforms that a loader must keep: the mug body is shifted 6 mm, the mug handle is turned 90° about Z, and the book block is centered and lifted onto y = 0.

### Manifest form

```json
{
  "schema_version": 2,
  "room_version": 1,
  "units": "meters",
  "frame": "y_up_right_handed",
  "pivot": "bottom_center",
  "quaternion_order": "xyzw",
  "entities": [
    {
      "id": "book", "label": "Book", "asset": "book.glb", "node": "book",
      "kind": "movable", "selectable": true,
      "size": { "width": 0.2, "height": 0.04, "depth": 0.15 },
      "position": { "x": -0.2, "y": 0.75, "z": -1.05 },
      "rotation": { "x": 0.0, "y": 0.2588, "z": 0.0, "w": 0.9659 }
    }
  ]
}
```

`units`, `frame`, `pivot` and `quaternion_order` must have exactly these values. A manifest that declares anything else is refused rather than reinterpreted.

### Placement happens once

The manifest is the only placement. The referenced node and every ancestor must have no transform; Python refuses a GLB whose entity node carries a translation, rotation, scale or matrix. Transforms on the node's descendants are part of the asset and are kept. Both clients drop the node's own and ancestor transforms and give each entity one placement root at the manifest position and rotation. For the stand-in room, the node translation equals the manifest position, so dropping it does not move anything.

### Validation

The legacy checks still apply to the stand-in room, including exactly one movable entity. The second form has its own rules:

- Entity IDs are unique, and each asset/node pair is used once. Static entities are not selectable; movable entities are selectable. There is no limit on how many are movable.
- Asset names match `name.glb` and must sit in the room directory. GLB files must be self-contained, with geometry in their binary chunk.
- The node name appears once in its file and is not also a mesh, scene or camera name. Three.js renames one of two equal names, so the browser could otherwise resolve the wrong object. Node names cannot contain `.`, which Three.js strips.
- An entity's node must not sit inside another entity's node. Its subtree must contain geometry.
- Mesh extents from the POSITION accessor `min`/`max`, transformed through the descendant nodes, must equal the declared size around a bottom-center pivot within 0.1 mm.
- Rotations must be within 0.001 of unit length. They are normalized when loaded.

A missing, corrupt or mismatched asset makes the room unavailable with a message naming the asset or entity. If an asset passes these checks but cannot be loaded in a browser, that client shows the asset name and does not draw a partial room.

### Choose the served room

Python serves `assets/prepared-room/` by default. Set `ESCAPE_ROOM_PREPARED_DIR` to serve another room directory:

```bash
ESCAPE_ROOM_PREPARED_DIR=assets/multi-asset-room .venv/bin/python -m uvicorn backend.app:app --host 127.0.0.1 --port 8000 --workers 1 --ws-max-size 16384
```

Assets are served under `/assets/prepared-room/` whichever directory is chosen.

### What was checked

Automated checks connect both roles to each fixture and check the same version, IDs and entity records. Moving the mug leaves the book, table and floor unchanged, and moving the table is rejected. Every GLB is served, and corrupt, transformed or mismatched assets are refused. In Chromium, both fixtures load on both pages, and a corrupt asset shows a visible failure. The real placement code, run against the served assets, produces world bounds matching each declared size, position and rotation.

These are desktop checks. iPhone and Quest have not loaded the multi-asset room yet.

## Splat rooms (issue 92)

A schema 2 room can name a Gaussian splat, trained from a video of a real room with the [room splat notebook](../spikes/colmap-splat/README.md). Both devices then draw the splat as the room:
- **Static entities are not drawn, but stay in force.** The phone's walking keeps to the floor, and aiming stops at furniture.
- **Movable entities are drawn over the splat** and are picked up as usual.
- **The splat is in the room frame already:** meters, +Y up, floor at `y = 0`.

```json
"splat": { "asset": "room.ply" }
```

**Validation:** the asset must be a plain `.ply` or `.spz` file name in the room folder. Python checks that it exists and starts like its format (`ply` text for PLY, gzip for SPZ). A missing or wrong splat makes the room unavailable with a reason, like a missing model. `GET /api/room` and each device's state carry `splat_url`, or `null` for rooms without a splat.

**What devices load:** Spark, the splat renderer, is downloaded only for splat rooms, so other rooms stay as light as before. In a splat room the headset page's overview starts at the room origin facing −Z, where the video was filmed, instead of the stand-in room's corner view.

**Make one from a notebook download** (`room.ply` and `report.json`):

```bash
python assets/splat-room/build_room.py ~/Downloads/room-splat data/splat-room
```

It writes `data/splat-room/` (git ignores `data/`):
- the splat;
- a floor entity covering the middle 90% of the splat, and at least 2 m square, so walking stays in the room;
- a 0.3 m movable box, 1 m in front of the middle filmed viewpoint;
- the manifest.

Each rebuild counts the room version up, so devices still showing the earlier room load the new one. Serve it by setting `ESCAPE_ROOM_PREPARED_DIR=data/splat-room`, in `.env` or the shell, then start Python.

`assets/splat-room/` is the committed test room: a 107 KB synthetic splat of a checkered floor and a red block, with the same floor and box. It is rebuilt with `python assets/splat-room/build_room.py`.

**Limits:**
- **No furniture entities.** Walking passes through the splat's furniture, since there are no furniture entities for it to stop at.
- **Approximate scale.** It comes from the notebook's assumed 1.4 m camera height until the room is measured.
- **Gaps away from the filming.** Away from where the video was filmed, the splat shows gaps and smears.
- **Weight on phones.** A splat of 400,000 splats is about 42 MB and heavy for low-end phones.

### Render-and-ask (issue 98)

Python can render a splat room from any viewpoint and ask Qwen about the views, so later AI stages can look at the reconstructed room itself, not only at the photos. `backend/room_views.py` provides:
- **`render_views(room_dir, views)`** draws the room's splat, placed as its manifest says, from each `View` (position, look-at point, field of view, size), in room metres. It runs Spark, the renderer the devices use, in headless Edge through `frontend/scripts/render-views.mjs`. It needs Node and a built frontend (`npm run build`, which builds `render.html`), but no GPU.
- **Viewpoint helpers:**
  - `orbit(target, distance, count, height)`: views round a target;
  - `filmed(room_dir)`: the cameras the video was filmed from, read from the notebook's `report.json`, which `build_room.py` now copies into the room;
  - `standing(spot, look_at)`: a player standing at a spot, at eye height;
  - `overhead(target)`: looking straight down.
- **`ask_about_views(client, views, question, answer, on_reply)`** sends 1–7 views, labelled "View 1"…, and the question through the OpenRouter adapter. It uses that adapter's answer formats, bounded repairs and failure kinds, and passes every reply to `on_reply` for recording. `SHORT_ANSWER` reads a few-word answer; add `SHORT_ANSWER_REQUEST` to the question, or Qwen explains at length.

A real run with the key from `.env` saves the views and a report under `data/room-views/`:

```bash
python -m backend.room_views_check data/splat-room "What object is at the centre of this view?" \
  "0,1.6,0@-0.5,0.15,-1.57" "orbit:-0.5,0.15,-1.57:1.2:1.2:4:1,4,2"
```

That is the recorded run: one view from the room origin and three round the waste bin, the last of them standing inside the wall behind it. The first three were answered "trash bag", "trash can" and "plastic bag".

**Measured on the hallway room (26 October 2026, laptop without a GPU):**
- **Rendering:** 0.16–0.42 s per 640×480 view. Starting the browser and loading the 42 MB splat takes about 2 s.
- **Asking:** each view cost about $0.00009 (338 prompt tokens) and took 2–4 s.

**Limit: viewpoints can be bad.** A view from where the camera never stood can stand inside a wall and show only smears, and Qwen may still name something ("light source"). Choose viewpoints within the filmed space, near `filmed` views, until views are checked before asking.
